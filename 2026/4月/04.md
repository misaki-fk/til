学び
- controllerで helper_method に登録すると viewでも使える
`helper_method :current_group`
- グループ機能は「UserではなくGroupを中心」に設計する
- データは「User → Group → Bread」の関係にするのが拡張性高い
- 中間テーブル（Membership）で多対多を実現する
- 既存データ移行は「nullable → データ埋める → NOT NULL」の順で行う
- migrationは構造変更＋データ移行をセットで考える
- up/downは「進む/戻る」で、データ移行は戻せないことが多い
- 本番とローカルのDBは別なので、データ移行は本番でも必要
- association（has_manyなど）を忘れるとNoMethodErrorになる
- current_userではなくcurrent_groupでデータ取得するのが重要
- セキュリティ的にも Group経由でfind するのが必須
- helper_methodを使うとcontrollerのメソッドをviewでも使える
- UIは「ホーム1つ＋グループ切り替え」がシンプルで正解
- sessionを使うとグループ切り替え状態を保持できる
- importmap環境ではJS関数は window. に生やさないと使えない
- Turbo使用時は turbo:load でイベント登録する必要がある
- CSSで中央寄せしたい場合、flexよりgridが安定することがある
- absolute配置は「top/left両方」を指定しないとズレる
- 幅固定（w-16）はレイアウト崩れの原因になることがある
- モデルは「正しい値」、ビューは「見せ方」を担当するべき
- UIの違和感に気づくことがプロダクト品質を上げる

フラッシュメッセージがヘッダーの上に来たり
消える時にメインに不自然の余白が生まれる

問題と解決の流れ
① メインコンテンツが押し下がる
フラッシュをDOMの流れに置くと、表示/非表示のたびにレイアウトが動く。
→ position: absolute で浮かせてレイアウトから切り離す。
② ヘッダーより上に出てしまう
ビュー側で render "layouts/header" を直接呼んでいたため、application.html.erb のフラッシュより後にヘッダーが描画されていた。
→ ビュー側を content_for :header に統一し、描画順を正しくする。
③ 消えるときに白くチラつく
opacity や max-height アニメーションはレイアウトに影響する。
→ translateY に変更。レイアウト非依存でGPU処理されるため滑らか。
④ ヘッダーの裏に潜れない
ヘッダーが z-10、フラッシュが z-50 では、フラッシュが常に前面に出てしまう。
→ ヘッダーを z-20、フラッシュを z-[9] にして前後関係を逆転。

## 4/27
nullableとoptional: trueの意味が似ていて混同

Railsモデル
```
belongs_to :bread, optional: true
```
関連のルール

DBマイグレーション
```
t.references :bread, null: true
```
カラムのルール

| 概念    | 書き方            | 役割          |
| ----- | -------------- | ----------- |
| Rails | optional: true | モデルのバリデーション |
| DB    | null: true     | DBの制約       |
